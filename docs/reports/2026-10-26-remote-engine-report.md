## Deviations and decisions

- **Engine interface.** The spec's `start / pushAudio / finish / cancel` became `prepare()` + `start(options)` + `push` / `finish`, with cancel through the `AbortSignal` the session already used. `prepare()` exists so the server connection (and therefore "is the server reachable") is settled before any audio is sent and selection never happens mid-session.
- **Local -> server fallback.** The explicit permission is the order "Lokálne, potom server" itself; its description says that audio is then sent to the server.
- **Pairing outcome** returns the device id instead of the whole pairing (the pairing is saved by `DevicePairing` itself).
- **Latency** on the Server page is the time to open the encrypted session (`hello` -> `ready`), labelled "Pripojenie"; there is no separate ping message in the protocol. Route auto-detection (LAN/WireGuard/Cloudflare) is not implemented; the card shows the endpoint host.
- **`server_key_changed` detection.** Besides the explicit error code, a handshake the server rejects with `bad_message` before replying and a reply that does not authenticate are both treated as a changed key, because the pinned key no longer matches. The status stays "Treba znova spárovať" and every dictation fails fast until a new token is pasted.
- **Disconnect** also switches an engine order that uses the server back to Lokálne, so the next dictation does not fail with "Server nie je spárovaný".
- **E2E vault.** In e2e mode (`CW_E2E_HOOKS=1`, never in packaged builds) the app uses `InsecureTestVault` (fixed-key AES-GCM) so tests never trigger a Keychain prompt.
- **E2E gateway** runs in a child process via `tsx` (new desktop dev dependency `tsx` 4.23.15) because the e2e TypeScript project includes the DOM lib, which conflicts with the server's `fetch` body types.
- **Partials.** No `partials` field is sent yet. Stream F confirmed the shape (`start.partials?: boolean`, absent = Indikátor); `partial` messages are already accepted and ignored, so wiring Živý text later is a one-line change plus an overlay consumer.
- **Overlay action for server errors** still opens Nastavenia (where the engine section points to the Server page); a dedicated "open Server page" action was left out to keep the overlay contract change minimal.

## Reviews

- **gpt-6.1-sol** (`codex exec -m gpt-6.1-sol -s read-only`, whole branch, correctness and security focus): 5 findings, all P2, all accepted and fixed test-first in `cf16f92`:
  1. The retry buffer could overflow while the reconnect was in flight and the retry then replayed an empty or truncated recording. `resume()` now checks the buffer and fails with the text so far. Test: `fails instead of replaying a truncated recording when the buffer overflows during the reconnect`.
  2. A pairing approved just before a cancel or a disconnect could still be written after the disconnect cleared the file. `DevicePairing` checks the signal after the approval, `EncryptedPairingFile` serializes saves and clears, and `disconnect()` detaches the running pairing. Tests: `applies saves and clears in the order they were requested`, `a disconnect during a pending pairing leaves nothing paired`.
  3. A reconnect reloaded the current pairing and could replay the recording to a different, newly paired server. `ServerConnector.reconnect(previous)` only reconnects to the same device id, endpoint and server key. Test: `does not replay the recording to a different server after the pairing changed`.
  4. A dictation cancelled while the server connection was still opening could still be started (and its idle timer could reconnect). `DictationSession.finish` checks the abort after awaiting the preparation, and `RemoteDictation` sends nothing for an already aborted signal. Tests: `never sends anything for a dictation whose signal is already aborted`, `a dictation cancelled while the server connection is still opening sends nothing`.
  5. A paired server could send `segmentId: 4294967294` and make the client allocate a huge array. Segments are now a `Map`, ids above 4095 and transcripts above 200,000 characters are protocol errors. Tests: `rejects a segment id far beyond any real dictation`, `rejects a transcript that grows beyond the overall text limit`.
- **CodeRabbit** (`coderabbit review --agent --base main`): the first attempts hit the shared free-tier rate limit (other streams use the same allowance); the run after the fixes completed on all 84 files with 0 findings.
- Own review while implementing: the frame listener leaked when the microphone failed to start; fixed in `f262643` with a test.
